# Full Bias Analysis Pipeline (A to Z)

This document describes the complete internal bias-analysis pipeline from the moment a bias run starts to the moment all analytics tables are finalized.

## 1. Pipeline Initialization

1. The pipeline starts by initializing run state, run logs, and timing metadata.
2. Bias-related tables are verified/created before computation starts.
3. The run context records which clustering source is used:
   - internal clustering
   - externally provided clusters
4. Default analysis configuration is loaded (embedding provider/model key, lookback window, thresholds).

## 2. Article Cohort Selection

1. Articles are loaded from the `Article` table using a rolling lookback window (default 28 days).
2. Only articles with usable text are included:
   - `text` is present
   - text length is above minimum threshold
3. The resulting set becomes the analysis cohort for the run.
4. If no valid records exist, the run exits with a clean no-data result and persists logs.

## 3. Outlet Context Derivation

1. Distinct outlets in the cohort are collected.
2. An outlet token blocklist is built to reduce publisher-name leakage into topic semantics.
3. This blocklist is later applied during text preparation and label sanitization.

## 4. Analysis Text Construction

For each selected article, the pipeline builds a model-ready analysis string:

1. Start from title, sentence snippets, entities, and body text.
2. Apply weighting strategy:
   - title repetition to strengthen topic signal
   - early-sentence preference
   - optional entity hints
3. Strip outlet markers and normalize whitespace/content.
4. Enforce configured char/sentence limits so payload size is controlled.

The output of this phase is one cleaned analysis text per article.

## 5. Embedding Model Resolution

1. The embedding provider is resolved (`local` by default).
2. Local model key `mpnet_v2` resolves to model `all-mpnet-base-v2`.
3. Optional Gemini embedding path is supported via environment configuration.
4. Active embedding model identity is logged for run traceability.

## 6. Embedding Generation

1. The analysis texts are embedded into dense vectors.
2. Local path uses sentence-transformer encoding with normalized embeddings.
3. Gemini path (when configured) uses batched embedding requests.
4. Vector generation statistics are logged (input sizes, completion state).

## 7. Embedding Upsert Persistence

Each article embedding is upserted into `ArticleEmbedding` with:

1. `article_id`
2. `outlet`
3. `embedding_provider`
4. `embedding_model`
5. `embedding_dimensions`
6. embedding vector payload
7. source text hash
8. timestamps

This ensures reproducibility and version-safe reprocessing.

## 8. Aligned Analysis Matrix Build

1. The pipeline reloads embeddings for the current provider/model.
2. Rows are aligned to article metadata and prepared texts.
3. An analysis matrix is built:
   - ordered article rows
   - ordered text rows
   - aligned embedding tensor
4. If fewer than two aligned rows exist, the run exits as insufficient for topic grouping.

## 9. Topic Group Construction (Internal Source)

When internal grouping is used:

1. Agglomerative clustering runs on embeddings (`cosine` metric, average linkage).
2. Distance threshold comes from:
   - explicit env override, or
   - adaptive threshold computed from pairwise corpus distances
3. Initial clusters are post-processed for quality:
   - split oversized clusters
   - split low-coherence clusters
   - split outlet-dominated clusters
4. Single-outlet clusters may be merged with compatible clusters if semantic similarity is strong and size remains bounded.

Result: cluster map from cluster label to article indices.

## 10. Topic Group Construction (External Source)

When external clusters are provided:

1. Cluster payloads are normalized and validated.
2. Article IDs are mapped into the current run’s cohort.
3. Invalid, duplicate, or too-small groups are dropped.
4. Accepted groups preserve provided topic metadata (topic key/label).

Result: validated external cluster map plus topic metadata overrides.

## 11. Topic Label Generation Strategy

For clusters that need labels, the pipeline uses layered fallback logic:

1. Batch LLM labels (Gemini) when available.
2. Most-central title fallback from cluster semantic center.
3. KeyBERT keyphrase extraction fallback.
4. Sanitized fallback title if needed.

All labels are cleaned to remove outlet artifacts and low-information tokens.

## 12. Topic Key Strategy

Topic IDs are made stable across runs:

1. If external key exists, it is used directly.
2. Otherwise, a stable key is generated by hashing a quantized cluster centroid signature with domain context.

This supports cross-run comparability.

## 13. Sentiment Inference

1. Sentiment model is loaded from environment configuration:
   - primary key: `SENTIMENT_MODEL`
   - fallback key: `BIAS_SENTIMENT_MODEL`
   - default fallback: `cardiffnlp/twitter-roberta-base-sentiment-latest`
2. Long article handling uses chunked sliding-window inference:
   - fixed chunk size
   - overlap between chunks
   - lead chunk receives extra weight
3. Chunk outputs are aggregated into:
   - final label (`positive`, `neutral`, `negative`)
   - confidence
   - scalar sentiment score in `[-1, 1]`

## 14. Cluster Eligibility Filters

Before scoring a cluster:

1. Clusters with a single outlet are skipped.
2. Clusters below minimum outlet diversity are skipped.
3. Skipped counts are tracked by reason for run diagnostics.

## 15. Coverage Semantics

For each scored topic cluster:

1. Coverage ratio is computed as covered outlets over total active outlets.
2. A cluster is considered a majority topic when ratio meets configured threshold.
3. Majority status drives omission/coverage bias accounting at outlet level.

## 16. Emphasis Bias Computation

Within each scored cluster:

1. Article lengths are measured from clean/raw text.
2. Cluster mean length is computed.
3. Per-article emphasis bias is calculated:
   - `(article_length - cluster_mean) / cluster_mean`
4. Values are clamped to a bounded range.

Interpretation:

- positive value: more relative attention than peers
- negative value: less relative attention than peers

## 17. Article-Level Bias Scoring

For each eligible article in each eligible topic:

1. Sentiment bias is computed as:
   - `article_sentiment_score - reference_mean`
2. Reference mean usually equals cluster sentiment mean.
3. In outlet-dominance cases, reference logic is adjusted to avoid dominant-outlet distortion.
4. Each article is materialized as a scored record with:
   - topic key/label
   - sentiment label/score/confidence
   - sentiment bias
   - group mean
   - coverage flags
   - emphasis bias

## 18. Article Score Upsert

Scored records are upserted into `ArticleBiasScore` by article identity.
If an article already has a score row, it is updated with latest run values.

## 19. Outlet Statistics Accumulation

During cluster scoring, per-outlet accumulators track:

1. sum of sentiment biases
2. sum of sentiment scores
3. sum of emphasis biases
4. article count scored
5. topics covered
6. majority topics considered
7. majority topics missed
8. missed topic labels

Parallel outlet-topic accumulators are also built for topic-level scoring rows.

## 20. Outlet Profile Computation

After article scoring:

1. outlet averages are computed:
   - `sentiment_bias_avg`
   - `sentiment_score_avg`
   - `emphasis_bias_avg`
2. coverage gap is computed:
   - `coverage_bias_rate = coverage_missing_majority / topics_considered`
3. composite BSI is computed from sentiment, coverage, and emphasis components.
4. source trust and misinformation-risk scores are derived from BSI, model confidence, evidence volume, and coverage quality.
5. outlet profile rows are upserted into `OutletBiasProfile`.

## 21. Topic-Level Outlet BSI Rows

For each outlet-topic pair in the run:

1. per-topic outlet averages are computed
2. coverage-present flag is carried
3. per-topic BSI is computed
4. rows are written to `OutletTopicBSI` keyed by `(run_id, outlet, topic_key)`

## 22. Snapshot Layer for Longitudinal Tracking

A snapshot is inserted per outlet into `OutletBiasSnapshot` for the run:

1. includes profile metrics and BSI
2. links to run ID and snapshot timestamp
3. includes source trust and misinformation-risk scores
4. provides a historical series for trend analysis

## 23. Omission Intelligence Layer

For each outlet snapshot:

1. recent historical snapshots are loaded (lookback run count).
2. historical average coverage gap is computed.
3. omission score is calculated as:
   - `current_coverage_gap - historical_average_coverage_gap`
4. systematic omission flag is assigned if score exceeds configured threshold.

This adds temporal bias behavior detection beyond single-run metrics.

## 24. Run Log and Final State Persistence

1. Full run logs are persisted into `BiasRunLog`.
2. Run state is finalized (`done` or `error`).
3. Final counters are returned from service layer:
   - processed article count
   - topics processed
   - profiles updated
   - embeddings saved
   - embedding provider/model metadata
   - cluster-source metadata

## 25. Final Artifacts Produced by One Run

A complete bias run produces:

1. model-versioned article embeddings
2. topic clusters with stable keys and labels
3. article-level bias scores
4. outlet-level bias profiles with BSI
5. outlet-topic BSI matrix rows
6. outlet longitudinal snapshots
7. omission/systematic-omission indicators
8. persisted run-level audit logs

## 26. Key Configuration Controls

Important environment-controlled controls include:

1. embedding model/provider selection
2. clustering thresholds and split/merge limits
3. topic diversity and outlet-dominance controls
4. sentiment chunk sizing and weighting
5. omission threshold and historical lookback depth
6. analysis text limits (sentences/chars/entities/title weighting)

These controls tune precision, robustness, and semantic stability of the pipeline.
